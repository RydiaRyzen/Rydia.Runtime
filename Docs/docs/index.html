はじめに

Rydia Engine の基本構成や、 GameStudio の役割について説明します。

Rydia Engine について

Rydia Engine は、ゲームの実行に必要な機能と、 エディターやランチャーで共通して使用するクラスを提供します。

エンジンとエディターの役割

Rydia Engine は、エディターとランチャーの 両方で使用される共通機能を提供します。

Rydia GameStudio は、ゲームオブジェクトの 作成・管理を行うための開発ツールです。

ランチャー要件

Rydia Engine Launcher の動作環境について説明します。

対応プラットフォーム

ランチャーは現在 Windows , Android専用です。 macOS および Linux , iOS, Nintendo Switch への対応も視野に入れています。

必要な環境

  • .NET 9.0
  • OpenGL ES 2.0 または 3.0 に対応した環境

グラフィックスバックエンド

現在は OpenGL ES を使用します。 グラフィックスバックエンドは今後追加する予定です。

エディター要件

Rydia GameStudio の開発環境について説明します。

対応プラットフォーム

エディターは現在 Windows 専用です。 macOS および Linux への対応も視野に入れています。

必要な環境

  • .NET 9.0
  • OpenGL ES 2.0 または 3.0 に対応した環境

プロジェクト構成

Rydia Engine のプロジェクトで使用するフォルダーについて説明します。

Assets

Rydia Engine Launcher で使用するゲームアセットを格納します。

Source

Media フォルダーと Code フォルダーを格納します。

Media

GameStudio でインポートした音楽、画像、 フォントなどの素材を格納します。

Code

ソリューションファイルやソースコードを配置します。 独自の Component を作成するには C# で実装します。

Getting Started

最初のプロジェクトを作成し、実行までの流れを確認します。

プロジェクトを作成する

Rydia GameStudio で新しいプロジェクトを作成し、テンプレートと保存先を選択します。

ソースコードを確認する

Source/Code フォルダーに生成されたソリューションとプロジェクトを確認します。

実行する

必要なランタイムとグラフィックス環境を用意し、プロジェクトをビルドして起動します。

Creating Bullet-like Objects

ゲーム内で弾のようなオブジェクトを作成する際の考え方を説明します。

オブジェクトを分ける

弾の位置、速度、寿命など、役割ごとのデータを整理します。

更新処理

フレーム更新時に位置を更新し、寿命や画面外判定に応じてオブジェクトを破棄します。

注意点

多数の弾を扱う場合は、生成・破棄の頻度や衝突判定の負荷を確認してください。

Working with Animations

アニメーションを扱うための基本的な構成を説明します。

アニメーション素材

連番画像やアニメーション用データをプロジェクトの素材として管理します。

再生状態

再生中・停止中・ループなどの状態を明確にし、更新処理と描画処理を分離します。

タイミング

フレームレートに依存しない時間管理を行い、再生速度を調整できるようにします。

Using Tilemaps

タイルを並べてマップを構成する際の基本事項です。

タイル素材

タイル画像とマップデータを分けて管理します。

マップ座標

セル座標とワールド座標の変換規則を統一します。

描画範囲

画面に表示される範囲を優先して描画すると、大きなマップの負荷を抑えられます。

Components

Component は、ゲームオブジェクトに機能や振る舞いを追加するための単位です。

責務を分ける

入力、移動、描画などの機能を独立したコンポーネントとして整理します。

独自 Component

プロジェクトの C# コードで必要なクラスを実装し、エンジンが定める規約に従って登録・使用します。

ライフサイクル

初期化、更新、終了時の処理がどのタイミングで呼び出されるかを、利用する API の仕様に合わせて実装します。

GameObjects

GameObject は、ゲーム内の要素をまとめて管理するための概念です。

オブジェクトの役割

プレイヤー、敵、カメラ、エフェクトなど、ゲーム内の要素をオブジェクトとして整理します。

構成

必要な Component を組み合わせ、オブジェクトごとの役割を表現します。

管理

生成・破棄のタイミングや、親子関係を使用する場合の所有関係を明確にします。

Resources

画像、音声、フォントなどのリソースを管理する際の基本事項です。

素材のインポート

GameStudio で利用する素材をインポートし、プロジェクト内で管理します。

読み込みと解放

リソースの読み込み時期と解放時期を決め、不要になった GPU・メモリ資源を保持し続けないようにします。

パスの管理

実行環境に依存する絶対パスではなく、プロジェクト内で一貫した識別方法を使用します。

Input Handling

キーボード、マウス、タッチなどの入力をゲーム処理へ渡す方法を説明します。

入力の取得

プラットフォームごとの入力差異を吸収し、ゲーム側では共通の入力 API を利用する構成にします。

イベントと状態

押下・解放イベントと、現在押されている状態を用途に応じて使い分けます。

複数プラットフォーム

タッチとマウスなど、入力方式が異なる場合もゲーム側の操作体系を整理します。

Audio Handling

ゲーム内の効果音や音楽を扱う際の基本事項です。

音声素材

対応形式の音声ファイルを Media フォルダーで管理します。

再生制御

再生、停止、音量、ループなどの制御を用途ごとに整理します。

リソース管理

音声デバイスやコンテキストの初期化・終了処理を適切なライフサイクルで実行します。

Logging

ログを使用して、実行時の状態や問題の原因を調査します。

ログの用途

初期化、リソース読み込み、例外など、調査に必要な情報を記録します。

ログレベル

情報、警告、エラーを区別し、通常運用時に必要な情報を見つけやすくします。

機密情報

パスワードやトークンなどの機密情報をログへ出力しないでください。

Guidelines

保守しやすいプロジェクトにするための一般的な指針です。

責務を明確にする

クラスやメソッドの役割を絞り、処理の依存関係を分かりやすくします。

命名と文書化

一貫した命名規則を使用し、公開 API には XML ドキュメントコメントを付けます。

エラー処理

失敗する可能性のある処理を把握し、原因を調査できる情報を残します。

Custom Renderers

独自の描画処理を追加する際に検討する項目です。

描画の責務

ゲームロジックと描画処理を分離し、描画に必要なデータを明確にします。

OpenGL リソース

バッファ、テクスチャ、シェーダーなどは、生成したコンテキストと適切なタイミングで管理します。

状態の管理

ブレンド、深度テスト、バインド状態など、描画状態の変更が他の描画処理へ影響しないようにします。

Version Control

Git などのバージョン管理を使用して変更履歴を管理します。

コミット

一つの目的に沿った小さな単位で変更を記録します。

除外設定

ビルド出力、一時ファイル、個人環境の設定など、共有不要なファイルを除外します。

競合の解決

競合箇所を確認し、意図した変更が両方残るように統合します。

Custom Editor Actions

エディターに独自の操作を追加する際の考え方です。

操作の設計

利用者が何を実行する操作なのかを明確にし、適切な名称と配置を選びます。

入力検証

実行前に選択状態や入力値を確認し、不正な状態で処理を開始しないようにします。

結果の通知

成功・失敗が分かるようにし、必要に応じてログやエラーメッセージを提示します。

Framework Structure

エンジン、ランタイム、エディター、ゲームプロジェクトの責務を整理します。

共通機能

複数のアプリケーションで利用する型や処理を共通ライブラリへまとめます。

プラットフォーム固有処理

OS やデバイスに依存する処理は、共通コードから分離して管理します。

依存関係

参照方向を整理し、共通ライブラリが特定のアプリケーションに依存しない構成を目指します。

Handling Object Data

ゲームオブジェクトのデータを保存・復元する際の注意点です。

保存対象

永続化する値と、実行時に再生成できる値を区別します。

形式と互換性

保存形式を変更する場合は、既存データとの互換性や移行方法を検討します。

検証

読み込み時に欠落値や不正な値を検出し、安全に扱えるようにします。

Using External Libraries

外部ライブラリを導入する際の確認事項です。

互換性

対象フレームワーク、対応 OS、CPU アーキテクチャを確認します。

ライセンス

配布形態に応じてライセンス条件と著作権表示を確認します。

依存関係

必要な DLL やネイティブライブラリを把握し、実行環境へ正しく配置します。

Package Management

パッケージと依存ライブラリを管理する際の基本事項です。

バージョンの固定

再現性のため、利用するパッケージのバージョンを明確にします。

更新前の確認

破壊的変更、対象フレームワーク、ライセンスを確認してから更新します。

配布物

実行に必要な管理 DLL とネイティブ依存ファイルが含まれているか確認します。

How to Contribute

Rydia Engine への変更を提案する際の基本的な流れです。

変更内容を確認する

既存の Issue やドキュメントを確認し、変更目的と影響範囲を整理します。

変更を分離する

目的ごとにブランチを作成し、関連する変更をまとめます。

提出前の確認

ビルド、動作確認、必要なドキュメント更新を行ってから変更を提案します。

Maintainer Guidelines

メンテナーが変更を確認・管理する際の確認項目です。

レビュー

設計、互換性、テスト、ドキュメントの観点から変更を確認します。

リリース管理

変更内容とバージョンを整理し、利用者が影響を判断できるようにします。

継続的な保守

未解決の問題や依存ライブラリの更新状況を定期的に確認します。

Branch Descriptions

リポジトリのブランチの役割を記載するページです。

ブランチの目的

開発用、修正用、リリース用など、各ブランチの用途をここに記載します。

運用ルール

マージ先、保護設定、削除条件などは、実際のリポジトリ運用に合わせて定義します。

Development Cycle

機能追加からリリースまでの開発サイクルを整理します。

計画

目的、要件、影響範囲を明確にします。

実装と検証

実装後にビルドや対象プラットフォームでの動作を確認します。

リリース

変更点、既知の問題、必要な移行手順をまとめて公開します。

List of Community Projects

Rydia Engine を利用したコミュニティプロジェクトを紹介するページです。

掲載情報

プロジェクト名、説明、公開 URL、ライセンスなど、掲載に必要な情報を整理します。

掲載について

掲載するプロジェクトやリンクは、確認できた情報を追加してください。

Changelog

Rydia Engine の変更履歴をまとめるページです。

変更履歴の記録

追加、変更、修正、既知の問題をバージョンごとに整理します。

リリースとの対応

公開したバージョンと変更履歴が対応するように管理します。
